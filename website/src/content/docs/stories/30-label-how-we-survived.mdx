Actionbase was deployed to production before it was "complete." It had to keep evolving while maintaining production contracts.

A lot of these conversations happened while walking along [streams in Pangyo](https://github.com/kakao/actionbase/discussions/9) (Tancheon and Unjungcheon). How could we build a state where even we could trust the system?

## Verification Layers {#verification-layers}

| Stage          | Method                                                      | Purpose                                          |
| -------------- | ----------------------------------------------------------- | ------------------------------------------------ |
| Development    | [Tests as Contracts](/stories/contracts/)                   | Define and protect promised behaviors            |
| Pre-Deployment | [Shadow Testing](/stories/shadow-testing/)                  | Verify new versions with production traffic      |
| Migration      | [Comparison Verification](/stories/migration-verification/) | Confirm Source DB and Actionbase data match      |
| Runtime        | [HBase Consistency](/stories/hbase-consistency/)            | Maintain consistency between State, Index, Count |

Each layer catches different types of problems. One layer isn't enough.

## Building Trust {#building-trust}

In the CQRS pattern, we know the correct answer. The original data exists. [Gift Wish](/stories/kakaotalk-gift-wish/)'s shadow read fits this context. We could verify whether the data Actionbase created matched the source of truth.

Through verification, confidence grew: **issues could be detected and corrected**.

As this confidence accumulated, we could trust Actionbase even when it was the ledger itself. This wasn't a design decision made upfront. It was trust earned through verification.

The goal isn't to prevent all failures—it's to detect and fix them before they matter.
