# Translation

Actionbase documentation is translated using a **Translation Memory (TM)**
workflow. English is the source language; translations are generated by
applying exact-match TM lookups to the English MDX files.

## Contributing translations

We welcome translation contributions! Here's what you need to know.

### Step-by-step example

Let's walk through translating a missing entry in the FAQ page (`{lang}` = your
target language, e.g. `ko`).

1. **Find the TM file**: Open `website/i18n/tm/{lang}/faq.yaml`.
   If the TM file does not exist yet, create it:
   ```bash
   python website/i18n/scripts/translation-memory.py --lang {lang} init
   ```
   This generates empty TM files (with `target: ""`) for all English docs that
   don't have one yet.
2. **Look for empty targets**: Search for `target: ""` — these are untranslated segments (MISS).
   ```yaml
   - source: "Why is it called Actionbase?"
     target: ""
     context: heading
   ```
3. **Add the translation**: Fill in the `target` field with your translation.
   ```yaml
   - source: "Why is it called Actionbase?"
     target: "Your translation here"
     context: heading
   ```
4. **Add yourself to contributors**: In the same file's `meta` section, add your GitHub username.
   ```yaml
   meta:
     contributors:
     - your-github-username
   ```
5. **Preview locally**: Validate and build to check your translation before pushing.
   ```bash
   # Validate — catches YAML errors or broken entries (no files written)
   python website/i18n/scripts/translation-memory.py --lang {lang} validate

   # Build — generates {lang}/*.mdx from TM
   python website/i18n/scripts/translation-memory.py --lang {lang} build

   # Start the dev server and open http://localhost:4321/{lang}/
   cd website && npm run dev
   ```
6. **Open a PR**: The CI validates your changes and rebuilds translated docs automatically.

> **Do not edit `{lang}/*.mdx` files directly** — they are generated from TM
> and will be overwritten on the next build.

### Finding documents that need translation

Run the status command to see which documents have untranslated segments:

```bash
python website/i18n/scripts/translation-memory.py --lang {lang} status
```

Look for documents with low coverage or high MISS counts. `{lang}` defaults to
`ko` if omitted.

### TM format

Each document has a YAML file at `website/i18n/tm/{lang}/{doc-path}.yaml`:

```yaml
meta:
  contributors:
  - alice          # GitHub username or model identifier
entries:
- source: "Core Concepts"
  target: "Translated text"
  context: heading
- source: "Actionbase is a database for serving user interactions."
  target: "Translated text for the paragraph"
  context: paragraph
```

- **`meta.contributors`** — who contributed translations for this document
  (human usernames or model identifiers like `kanana-2`).
- **`entries[].source`** — English text (exact match key).
- **`entries[].target`** — translated text. Empty string (`""`) means untranslated (MISS).
- **`entries[].context`** — segment type: `frontmatter:title`,
  `frontmatter:description`, `heading`, `paragraph`, `table`, `list_item`,
  `summary`, `blockquote`.

### Glossary

Before translating, check the glossary at `website/i18n/glossary/{lang}.yaml`
for canonical translations of domain terms and terms that must remain in English.

```yaml
# website/i18n/glossary/{lang}.yaml
version: v1
terms:
  Edge: "translated term"
  Query: "translated term"
preserve:
  - Actionbase
  - HBase
```

- **`terms`** — domain terms with their canonical translations.
- **`preserve`** — terms that must remain in English.

The glossary is a reference for translators (human or LLM). The build script
does not auto-apply glossary substitutions — it only reads the `preserve` list.

### What happens after your PR

When you open a PR that touches TM files, the CI pipeline:

1. **Validates** — runs `translation-memory.py validate` to ensure all TM entries
   produce a successful build without errors.
2. **Reports status** — shows a translation coverage table for affected documents
   in the Job Summary, so you can see how your changes improve coverage.
3. **On merge** — the translation workflow rebuilds `{lang}/*.mdx` files and
   opens an automated PR with the updated translated docs.

## How it works

```
en/*.mdx ───┐
            │   ┌──────────────┐   ┌─────────────┐   ┌──────────┐
tm/*.yaml ──┼──▶│ Parse MDX    │──▶│ TM Lookup   │──▶│ Generate │──▶ {lang}/*.mdx
            │   │ (segments)   │   │ exact match │   │ output   │
glossary ───┘   └──────────────┘   │ HIT→target  │   └──────────┘
                                   │ MISS→source │
                                   └─────────────┘
```

1. `translation-memory.py build` parses each English MDX into **segments**
   (title, description, headings, paragraphs, tables, list items).
2. Each segment is looked up in the document's TM file by exact string match.
3. **HIT** — the translated text replaces the English segment.
4. **MISS** — the English text is kept as-is (easy to spot and fix).
5. Non-translatable content (code blocks, imports, JSX, images) passes through
   unchanged.

## File structure

```
website/i18n/
  tm/{lang}/{doc-path}.yaml    # Translation Memory per document
  glossary/{lang}.yaml         # Glossary (translated terms + preserve list)
website/src/content/docs/
  *.mdx                        # English source (authoritative)
  {lang}/*.mdx                 # Generated from TM — do not edit directly
website/i18n/scripts/translation-memory.py  # TM tool (init / update / build / validate / status)
TRANSLATION.md                 # This file
```

## Quick start

```bash
# Create empty TM files for new EN docs
python website/i18n/scripts/translation-memory.py init

# Sync existing TM with updated EN source
python website/i18n/scripts/translation-memory.py update

# Rebuild translated docs from TM
python website/i18n/scripts/translation-memory.py build

# Validate TM without writing files (exit 1 on errors)
python website/i18n/scripts/translation-memory.py validate

# Check current translation coverage
python website/i18n/scripts/translation-memory.py status

# Target a different language (default: ko)
python website/i18n/scripts/translation-memory.py --lang ko status
```

## Updating TM after EN source changes

```bash
python website/i18n/scripts/translation-memory.py update
```

The `update` command syncs existing TM files with updated English source docs:
- **New segments** are added with an empty `target` (ready for translation).
- **Stale entries** (source text no longer in EN) are removed.
- **Existing translations** are preserved intact.

Run `update` whenever English source docs change, then fill in empty targets.

## Script architecture

`translation-memory.py` (~1000 lines) is a single-file CLI with five
subcommands: `init`, `update`, `build`, `validate`, `status`.

### MDX parser

The core of the script is an **MDX line-by-line state machine** that
recognizes:

- Frontmatter (`---` blocks)
- Code fences (`` ``` ``/`~~~`)
- Headings (`#`..`######`), with explicit `{#id}` anchors
- Tables (header + separator + data rows)
- List items (unordered `- *` and ordered `1.`) with continuation lines
- Aside/details/summary JSX blocks
- Import/export statements, images, self-closing JSX (skipped)
- Blockquotes (`>` lines)

### Validate

`validate` runs the full build pipeline (`build_translated_doc()`) for every
document that has a TM file, but **writes no files**. It verifies:

- TM YAML files parse without errors.
- Every TM entry can be applied to its source document without exceptions
  (e.g., malformed regex, encoding issues, broken frontmatter).

If any document fails, the command prints the error list and exits with code 1.
This is used in CI to gate PRs that touch TM or source docs.

### Two walkers

The parser appears in two functions:

| Function | Purpose |
| --- | --- |
| `extract_segments()` | Parse MDX → list of `Segment` objects (text + type) |
| `build_translated_doc()` | Parse MDX → translated MDX string (TM lookup per segment) |

Both share the same state machine structure (code block tracking, aside
detection, list continuation merging, etc.) but differ in what they do at
each branch:

- `extract_segments` **collects** text into `Segment` data objects.
- `build_translated_doc` **emits** translated lines, handling output concerns
  like table column padding, text wrapping, link rewriting, and heading
  anchors.

The duplication is intentional — merging them into a single visitor would
require a callback interface complex enough to hurt readability. Each function
can be understood independently.

### Multi-language support

All paths are parameterized by `--lang`:

- TM: `website/i18n/tm/{lang}/`
- Glossary: `website/i18n/glossary/{lang}.yaml`
- Output: `website/src/content/docs/{lang}/`
- Links: `/{lang}/foo/` prefix

Currently only `ko` has TM data. Adding a new language requires creating
`website/i18n/tm/{lang}/` YAML files and `website/i18n/glossary/{lang}.yaml`.

## Known limitations

- **Exact match only** — any change to an English segment requires updating
  the corresponding TM entry. There is no fuzzy matching. Use `update` to
  detect new/stale segments automatically.
- **Multi-line JSX components** (e.g., `<LinkCard>`) — passed through and may
  reformat slightly.
